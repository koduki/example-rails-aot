# GCE log investigator

Use the [formal report guidance](../gce-benchmark-runbook/references/report-writing.md) for eligibility and the current `scripts/bench/run.py`, `capacity.py`, profile, and `bench/k6/read.js` for the actual measurement contract. This skill is an investigation aid; it does not change the benchmark runner or certify a trial.

1. Download the complete raw release artifact. Verify its published SHA-256 before extraction; reject absolute paths, `..` paths, symlinks, and device entries in untrusted archives. Keep each run and workload in a separate directory. Record release URL, archive hash, `env.json` commit/profile hash/image IDs, `plan.json` workload/fixture/CPU/tester placement, and preflight eligibility. Never combine the three-article Actions smoke and the 1,000-article C3 cohort.
2. Run `python3 .agents/skills/gce-log-investigator/scripts/summarize.py PATH_TO_RUN > investigation.json` (optionally `--target spinel`). `PATH_TO_RUN` contains `plan.json`, `env.json`, and `trials/`. It reads raw per-window `k6-summary.json` without duplicating embedded k6 `raw` metrics in output. Inspect the JSON's `warnings` and `missing` fields, not just its target totals. If an artifact is absent, record it as missing rather than zero.
3. For each `(target, repetition)`, reconcile `trials/per-run.json`, `trial.json`, and every available window. Inspect `warmup-*/k6-summary.json`, `k6.log`, tester telemetry, `cpu.stat`, memory, server/GC/JFR logs, and `capacity-search.json`. The current k6 summary labels closed-loop warmup as `k6-open-arrival` and carries `rate_offered: 100`; the executor actually uses `constant-vus`. Report warmup as configured VUs and observed successful RPS. Use offered RPS only for open-arrival steps.
4. Classify separately: correctness/preflight failure, SUT error or timeout, invalid client (drops, tester saturation/network errors or insufficient issuance), artifact transfer/missing data, warmup instability, and confirmed SLO failure. Use the actual profile thresholds and code, not a universal p99 or error threshold. `p99` from mixed successes/failures needs the error count next to it; a zero/missing p99 is not evidence of good latency.
5. Diagnose the first failing phase and its lower healthy neighbor. Form explicit competing hypotheses, identify the required server and client evidence, and propose a discriminating low-load/step-load test. For CPU, divide cgroup usage delta by elapsed time, check throttling, and align time windows; average CPU alone cannot establish the blocked stack. Do not infer a cause from a shared startup warning or a correlation alone. Preserve complete failed trials.
6. Report all repetitions and unavailable comparisons. Fixed-rate short passes show health at that rate and duration; closed-loop successful RPS is a diagnostic; neither establishes sustainable capacity. Compute paired ratios only for the same-repetition trials that both passed valid 120-second confirmation, as in `capacity.paired_ratios`. Compare memory at the same offered rate, duration, and container metric definition. Link every claim to a path, phase, repetition, and command, and separate observation, inference, and next experiment.

For Spinel timeout, JRuby Off, and 1,000-article trend investigations, see [#54](https://github.com/koduki/example-rails-aot/issues/54), [#55](https://github.com/koduki/example-rails-aot/issues/55), and [#56](https://github.com/koduki/example-rails-aot/issues/56). These are hypotheses and protocols, not established causes.
